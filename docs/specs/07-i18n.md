# 07. 다국어 (한국어 / English / 简体中文)

> 다국어는 "문자열 번역"이 아니다. **날짜·숫자·통화·타임존·폰트·줄바꿈·정렬**이 모두 로케일에 따라 달라진다.

---

## 1. 지원 로케일

| 코드 | 이름 | 우선순위 | 비고 |
|---|---|---|---|
| `ko` | 한국어 | 기본 (소스 언어) | 모든 키의 원본 |
| `en` | English | 1차 확장 | 미지원 로케일의 폴백 |
| `zh-CN` | 简体中文 | 1차 확장 | **확정** — 3.0의 중국어는 간체만 |
| `zh-TW` | 繁體中文 | **3.1 예정** | 구조만 열어 둔다. 자형 변환이 아니라 별도 번역이 필요하다(§4.3) |
| `ja` | 日本語 | 3.2 예정 | 최대 시장이지만 3.0 범위 밖 |

**폴백 체인**: `zh-CN → en → ko`. 누락 키는 CI에서 막으므로 런타임 폴백은 안전망일 뿐이다.

## 3. 한국어 특유의 함정 ⭐

### 3.1 조사 (을/를, 이/가, 은/는, 와/과)

**문자열 결합으로 문장을 만들지 않는다.** 앞 단어의 받침 유무에 따라 조사가 달라지므로, 변수를 끼워 넣은 문장은 반드시 틀린다.

```jsonc
// ❌ 절대 금지
"delete.confirm": "{{name}}을 삭제할까요?"
//   → "도쿄을 삭제할까요?"  (받침 없음 → '를'이어야 함)

// ✅ 해법 1 — 조사가 필요 없는 구조로 문장을 다시 쓴다 (권장)
"delete.confirm": "삭제할까요?\n{{name}}"

// ✅ 해법 2 — 조사 선택 헬퍼 (불가피할 때만)
"delete.confirm": "{{name}}{{particle}} 삭제할까요?"
```

```ts
// src/shared/i18n/particle.ts
/** 한글 받침 유무에 따라 조사를 고른다. 한글이 아니면 뒤 조사(받침 없음)를 쓴다. */
export function particle(word: string, withBatchim: string, without: string): string {
  const last = word.trimEnd().at(-1);
  if (!last) return without;
  const code = last.charCodeAt(0);
  if (code < 0xac00 || code > 0xd7a3) return without;   // 한글 음절이 아님
  return (code - 0xac00) % 28 === 0 ? without : withBatchim;
}
// particle('도쿄', '을', '를') → '를'
// particle('부산', '을', '를') → '을'
```

> 숫자·영문으로 끝나는 단어(예: "Day 3", "KE801")도 받침 판정이 필요하다. 위 함수는 한글이 아니면 받침 없음으로 처리하는데, 실제로는 "1을/1을"처럼 발음 기준으로 달라진다. **가장 안전한 것은 해법 1이다.**

### 3.2 줄바꿈

현재 코드의 `* { word-break: keep-all }`은 한국어 어절 단위 줄바꿈을 위한 것이다. 중국어에 적용하면 긴 문장이 줄바꿈되지 않고 넘친다.

```css
:root:lang(ko) { word-break: keep-all; line-break: strict; overflow-wrap: break-word; }
:root:lang(en) { word-break: normal;  overflow-wrap: break-word; hyphens: auto; }
:root:lang(zh) { word-break: normal;  line-break: normal; }
```

`<html lang="{locale}">`을 언어 변경 시 갱신한다. (스크린리더 발음에도 영향을 준다)

## 4. 중국어 특유의 함정 ⭐

### 4.1 폰트

**Pretendard는 간체 중국어 글리프를 충분히 담고 있지 않다.** zh-CN에서 Pretendard만 쓰면 한자가 시스템 폰트로 폴백되어 두께·자간이 어긋나고, 일부 환경에서는 일본어 글리프로 렌더링된다(같은 유니코드, 다른 자형).

```ts
// 로케일 전환 시 폰트를 동적으로 로드
const FONT_BY_LOCALE: Record<string, string | null> = {
  ko: null,          // Pretendard (이미 로드됨)
  en: null,
  'zh-CN': 'https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@400;500;700&display=swap',
};
```

- **초기 번들에 넣지 않는다.** CJK 폰트는 서브셋이라도 수백 KB다.
- `display=swap`으로 로드 중에도 텍스트가 보이게 한다.
- CSP `style-src`/`font-src`에 Google Fonts를 추가해야 한다 (`vercel.json` 수정 필요).

### 4.2 문장 부호·간격

- 중국어는 단어 사이에 공백이 없다. 영문/숫자와 한자가 섞이면 `text-spacing`이 필요하다.
- 전각 문장부호(`，` `。` `：`)를 쓴다. 번역 시 반각(`,` `.` `:`)을 그대로 두면 어색하다 — 번역 검수 항목에 넣는다.

### 4.3 zh-TW 확장 여지

zh-CN과 zh-TW는 단순 자형 변환이 아니다 (어휘가 다르다: 软件/軟體, 网络/網路). 기계 변환으로 때우지 말고 별도 번역 파일을 둔다. 3.0에서는 구조만 준비한다.

## 5. 로케일별 포매팅

### 5.1 날짜

| 로케일 | 형식 | 예 |
|---|---|---|
| ko | `M/d (E)` | `5/20 (수)` |
| en | `MMM d (EEE)` | `May 20 (Wed)` |
| zh-CN | `M月d日 (E)` | `5月20日 (周三)` |

```ts
import { format } from 'date-fns';
import { ko, enUS, zhCN } from 'date-fns/locale';

const DATE_FNS_LOCALE = { ko, en: enUS, 'zh-CN': zhCN };
const DAY_HEADER_FORMAT = { ko: 'M/d (E)', en: 'MMM d (EEE)', 'zh-CN': 'M月d日 (E)' };
```

### 5.2 숫자·통화

`Intl.NumberFormat`을 쓴다. 직접 포매팅하지 않는다.

```ts
new Intl.NumberFormat('ko-KR', { style:'currency', currency:'JPY' }).format(9800);
// → "¥9,800"
new Intl.NumberFormat('zh-CN', { style:'currency', currency:'JPY' }).format(9800);
// → "JP¥9,800"
```

거리: `km`/`mi`는 `profiles.distance_unit`을 따르되, 기본값을 로케일로 추론한다 (en-US → mi, 그 외 → km).

### 5.3 타임존 ⭐

여행 앱에서 가장 헷갈리는 부분이다. **원칙을 고정한다.**

| 표시 대상 | 기준 타임존 |
|---|---|
| 일정 항목 시각 | **그 장소의 현지 시각** (기기 타임존 무관) |
| 항공편 출발/도착 | **각각 출발지·도착지 현지 시각** |
| D-day 카운트다운 | **사용자 기기 타임존** |
| 커뮤니티 글 작성 시각 | 상대 시간("6일 전") — 타임존 무관 |
| 푸시 알림 발송 시각 | 여행지 현지 시각 기준 |

```
❌ 흔한 버그: 서울에서 도쿄 일정을 보는데 08:00 항공편이 07:00으로 보임
✅ 해결: startLocal(문자열) + timezone을 저장하고, 표시할 때 변환하지 않는다
```

## 6. 서버 콘텐츠 다국어

| 대상 | 방법 |
|---|---|
| 여행지 이름·설명 | `destination_translations` 테이블 (locale별 행) |
| 푸시 알림 | 발송 시점에 `profiles.locale`로 템플릿 선택 |
| 서버 에러 메시지 | **에러 코드를 반환**하고 클라이언트가 번역. 서버가 한국어 문장을 내려보내지 않는다 |
| 이용약관·개인정보처리방침 | 3개 언어 정적 페이지 (`/terms/ko`, `/terms/en`, `/terms/zh-CN`) |
| App Store 리스팅 | 3개 언어 각각 작성 (설명·키워드·스크린샷) |

```ts
// ❌ 서버가 문장을 만들면 다국어가 불가능하다
return res.status(400).json({ error: '유효하지 않은 편명입니다.' });

// ✅ 코드로 반환
return res.status(400).json({ code: 'INVALID_FLIGHT_NUMBER' });
// 클라: t('errors:INVALID_FLIGHT_NUMBER')
```

> 기존 `api/flight.js`·`api/recommend.js`가 한국어 문장을 직접 반환한다. **Phase 6에서 에러 코드 체계로 전환해야 한다.**

## 8. 번역 워크플로

```
1. 개발자가 ko 키를 추가 (소스)
2. CI가 en / zh-CN 누락 키를 감지 → PR에 코멘트
3. 기계 번역으로 초안 생성 (scripts/translate-draft.ts)
4. 원어민 검수 (외주) — 검수 전 키는 "needsReview": true 마킹
5. 검수 완료 후 머지
```

**기계 번역 초안을 그대로 출시하지 않는다.** 특히 아래는 반드시 사람이 본다:
- 법적 문구 (약관, 개인정보처리방침, 계정 삭제 안내)
- 에러 메시지 (오해하면 사용자가 데이터를 잃을 수 있다)
- 결제·구독 문구 *(3.0에는 없음 — 4.0에서 추가될 때 적용)*

## 9. CI 검사

```ts
// scripts/check-i18n.ts
// 1) ko의 모든 키가 en, zh-CN에 존재하는가
// 2) 각 언어에 ko에 없는 고아 키가 있는가
// 3) 보간 변수({{name}})가 언어별로 일치하는가
// 4) ICU 플러럴 카테고리가 언어 규칙에 맞는가
//    (ko/zh는 other만, en은 one/other 필요)

```

5번이 특히 중요하다. 예외가 필요한 곳(로그 메시지 등)은 `// i18n-exempt` 주석으로 명시한다.

## 10. 의사 로케일 테스트

레이아웃이 긴 번역을 견디는지 검증한다.

```
ko: "저장"        (2자)
en: "Save"        (4자)
de: "Speichern"   (9자)  ← 독일어는 지원 안 하지만 레이아웃 스트레스 테스트용
의사: "[!!Sαvε!!]" (길이 +40%, 특수문자 포함)
```

`VITE_PSEUDO_LOCALE=1`로 빌드하면 모든 문자열이 40% 길어진 의사 번역으로 대체된다. Phase 6에서 전 화면을 이 모드로 점검한다.
