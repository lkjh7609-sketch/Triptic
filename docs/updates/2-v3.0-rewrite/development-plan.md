## 1. 현재 상태 진단 (2026-09-20, 실측)

개편 계획은 추측이 아니라 실제 코드 상태 위에서 세워야 한다. 아래는 저장소를 직접 확인한 결과다.

### 1.1 실측 수치

| 항목 | 실측값 |
|---|---|
| `index.html` | **8,254줄** (인라인 CSS 약 2,900줄 + 인라인 JS 약 5,000줄) |
| 모듈화된 `src/` | 13개 파일 (데이터 계층·유틸만) |
| 테스트 | Jest 5 suite / **47개 전부 통과** |
| 타입체크 | `tsc --noEmit` **통과** (단, `.ts` 파일은 2개뿐이라 커버리지 미미) |
| 커밋 수 | 110 |
| 프레임워크 | 없음 (Vanilla JS, `innerHTML` 문자열 렌더링) |
| 전역 상태 | `let plannerData/hotelsData/mealsData/expensesData/flightsData/dayCities` — 모듈 전역 가변 변수 |

### 1.2 이미 잘 되어 있는 것 (반드시 보존)

- **Google Maps 구간별 경로 렌더링** — `drawRoutesForViewMode()` (index.html:7057). 장소 간 `DirectionsService` TRANSIT 호출 → 실패 시 점선 폴백(`drawDashedFallback`), `directionsCache`로 중복 호출 차단. **이 앱의 핵심 차별점이며 3.0에서도 동일 알고리즘을 유지한다.**
- **일차별 다중 도시(`dayCities`)** 및 **존(zone) 분리** — `computeDayZones()`(index.html:6854)로 하루 안에서 지리적으로 떨어진 묶음을 감지해 따로 그린다. 장거리 이동이 섞인 일정에서 지도가 망가지지 않게 하는 좋은 장치다.
- **Supabase RLS 설계** — `supabase/schema.sql`. 소유자/공유 링크 분리, `SECURITY DEFINER` 함수의 만료·존재 검증까지 되어 있다. 3.0의 스키마는 이 설계 철학을 그대로 확장한다.
- **서버 전용 키 은닉** — `api/env.js`가 클라이언트 안전 키만 내려주고, `AVIATIONSTACK_API_KEY`는 `api/flight.js` 뒤에 숨어 있다. 레이트리밋·CORS 허용 목록도 구현됨.
- **AI 다중 폴백** — `api/recommend.js`가 Gemini → Groq → OpenRouter → 자체 큐레이션 순으로 폴백하며 전체 예산 8초를 지킨다. 이 폴백 패턴을 문서 파싱에도 재사용한다.

### 1.3 3.0을 막는 구조적 문제

| # | 문제 | 영향 |
|---|---|---|
| P1 | 8,254줄 단일 HTML + 전역 가변 상태 | 탭 4개·커뮤니티 피드·다국어를 얹으면 유지보수 불가능 |
| P2 | `innerHTML` 문자열 렌더링 + 수동 `escapeHtml` | 사용자 생성 콘텐츠(커뮤니티) 도입 시 XSS 위험이 구조적으로 커짐 |

| P4 | 하드코딩된 한국어 문자열 수천 개 | 다국어 불가 |
| P5 | `word-break: keep-all`이 `*`에 전역 적용 | 중국어 줄바꿈이 깨짐 (한국어 최적화가 zh에 역효과) |

| P7 | 계정 삭제 기능 없음 | **App Store 5.1.1(v) 위반 → 리젝 확정** |
| P8 | 로그인이 Google/Kakao 뿐 | **App Store 4.8 위반 가능성 높음** (§11 R3 참고) |

## 2. 제품 정의

### 2.1 한 줄 정의

> **예약 서류를 던져 넣으면 일정이 완성되고, 지도 위 동선과 날씨까지 한 화면에서 보이는 여행 플래너.**

### 2.2 세 가지 차별점

1. **지도 위 동선** — 경쟁 앱 대부분은 목록만 보여준다. Triptic은 구간별 실제 대중교통 경로를 그린다. *(기존 강점 유지)*
2. **서류 → 일정 자동 변환** — 항공권·호텔·렌터카·액티비티 PDF를 넣으면 날짜·시간·좌표까지 채워진 일정이 생성된다. *(신규, 핵심 차별점)*
3. **일정에 붙어 있는 바우처** — 필요한 순간(체크인 카운터 앞)에 원본 서류를 오프라인으로 즉시 꺼낼 수 있다. *(신규)*

### 2.3 타깃 사용자

- **1차**: 한국에서 일본·동남아·유럽으로 나가는 20~40대 개인 여행자 (직접 일정을 짜는 사람)
- **2차**: 동행자와 일정을 공유·조율하는 그룹 여행자
- **3차 (다국어 대상)**: 한국을 방문하는 영어권·중화권 여행자

### 2.4 성공 지표 (출시 후 90일)

| 지표 | 목표 |
|---|---|
| 서류 업로드 → 일정 반영 성공률 | **≥ 92%** (사용자 수정 없이 확정한 비율) |
| 서류 파싱 필드 정확도 (항공권 상위 10개 항공사) | **≥ 95%** |
| 여행 1개 이상 생성한 신규 가입자 비율 | ≥ 60% |
| D7 리텐션 | ≥ 25% |
| 크래시 프리 세션 | ≥ 99.5% |
| App Store 첫 제출 통과 | 1회 통과 |

## 4. 아키텍처 결정 (ADR)

### ADR-001. Vanilla JS 모놀리식 → **React 19 + TypeScript**로 전환

**결정**: UI 계층을 React 19 + TypeScript로 재작성한다.

**근거**:
- 3.0은 화면 수가 6개 → **약 25개**로 늘어난다. 8,254줄 단일 파일에 전역 변수로는 감당할 수 없다 (P1).
- 커뮤니티는 사용자 입력을 렌더링한다. React의 기본 이스케이프가 `innerHTML` + 수동 `escapeHtml`보다 구조적으로 안전하다 (P2).
- 문서 파싱은 **필드별 신뢰도를 가진 중첩 구조**를 다룬다. 타입 없이는 검수 UI를 안전하게 만들 수 없다.
- i18n·폼·가상 스크롤 피드 등 필요한 생태계가 이미 성숙해 있다.

**대안 검토**:
- *현행 Vanilla 유지*: 초기 속도는 빠르나 P1/P2/P4가 그대로 남는다. **기각**.
- *Svelte / Vue*: 기술적으로 충분하나, 채용·레퍼런스·Capacitor 사례가 React 쪽이 압도적. **기각**.
- *React Native / Flutter로 완전 네이티브화*: 지도·PDF·기존 Supabase 계층을 전부 재작성해야 하고, 웹(PWA) 배포를 잃는다. **기각**.

**보존 대상 (재작성 금지, 이식만)**:
- `drawRoutesForViewMode` / `computeDayZones` / `zoneCentroid` / `nearestZoneIndexForPoint` / `haversineKm` → `src/features/plan/map/` 로 **로직 그대로** 이식 후 단위 테스트 추가
- `src/services/supabaseService.js` → `.ts` 변환 + 신규 테이블 메서드 추가
- `src/utils/*` (dateUtils, timeUtils, escapeHtml, id) → 타입 추가 후 유지, 기존 47개 테스트 유지

**전환 전략 (Strangler)**: 빅뱅 재작성은 금지한다. Phase 1에서 React 셸을 세우고, Phase 2~4에서 화면을 하나씩 옮긴다. 계획(Plan) 화면이 기능 동등성(§10.3 패리티 체크리스트)을 통과할 때까지 기존 앱을 `/legacy`에 배포해 두고 언제든 되돌릴 수 있게 한다.

### ADR-002. 데이터 저장: `snapshot` JSONB → **정규화 테이블**

**결정**: 여행 데이터를 정규화 테이블로 옮긴다. `trips.snapshot`은 읽기 전용 레거시 컬럼으로 남기고, 이관 완료 후 제거한다.

**근거**: 대시보드가 요구하는 "방문 국가 수·총 이동 거리·총 여행 일수"는 JSONB 덩어리에서 집계할 수 없다 (P3). 커뮤니티 글이 일정을 참조하려면 항목에 안정적인 ID가 필요하다. 바우처는 일정 항목과 외래키로 이어져야 한다.

**이관 방법**: 양방향 쓰기(dual-write) 기간을 둔다. 상세 절차는 [`specs/03-data-model.md` §6](specs/03-data-model.md).

### ADR-003. 문서 파싱: **결정론적 파서 우선 + LLM 폴백**

**결정**: LLM에 PDF를 통째로 던지지 않는다. `규칙 기반 파서 → LLM 구조화 추출 → 결정론적 검증` 3단 파이프라인으로 만든다.

**근거**: 항공권 e-티켓은 포맷이 정형적이라 상위 10개 항공사는 규칙만으로 99% 잡힌다. 규칙이 먼저 걸러내면 비용·지연·환각이 모두 줄어든다. LLM 출력은 **반드시** IATA 공항 DB·날짜 범위·좌표 조회로 재검증한다. 상세: [`specs/04-document-ai.md`](specs/04-document-ai.md).

### ADR-004. 날씨: **Apple WeatherKit (REST)** 채택

**결정**: 1차 공급자는 Apple WeatherKit REST API. 서버 프록시 경유.

**근거**: Open-Meteo 무료 티어는 **비상업적 이용으로 제한**되며, 상업적 이용에는 유료 구독이 필요하다. App Store에 출시하는 앱은 비상업 예외에 기대면 안 된다. 반면 WeatherKit은 이미 필수로 가입해야 하는 Apple Developer Program($99/년)에 **월 50만 호출이 포함**되어 추가 비용이 0이다. 상세: [`specs/05-weather.md`](specs/05-weather.md).

### ADR-005. 서버: **Vercel Serverless 유지 + Supabase Edge Functions 병행**

**결정**: 기존 `api/*` (Vercel)는 유지하고, 인증·RLS 컨텍스트가 필요한 무거운 작업(문서 파싱, 모더레이션)은 Supabase Edge Functions로 보낸다.

**근거**: Vercel Hobby 함수 실행 시간 제한(기본 10초)은 기존 `api/recommend.js`가 8초 예산으로 회피 중이다. 대용량 PDF 파싱은 이 한계를 넘길 수 있다. Supabase Edge Function은 Storage·DB와 같은 네트워크 안에 있어 파일을 왕복시키지 않아도 된다.

| 분석 | PostHog (self-host 옵션) | — | 개인정보 최소 수집 |
| CI/CD | GitHub Actions + Vercel + Xcode Cloud | — | |

### 5.1 Tailwind를 쓰지 않는 이유

기존 디자인 토큰이 CSS 변수로 잘 정의되어 있고([`specs/01-design-system.md`](specs/01-design-system.md)), 다크 모드를 CSS 변수 교체로 처리하는 편이 단순하다. 또한 지도 오버레이·바텀시트처럼 동적 계산이 많은 UI는 유틸리티 클래스보다 CSS Modules가 읽기 쉽다. **팀이 Tailwind를 강하게 선호한다면 바꿔도 좋다 — 단, 토큰을 `tailwind.config`의 `theme.extend`로 그대로 옮기고 임의 값(arbitrary value) 사용을 금지할 것.**

## 7. 기능 명세 요약

각 항목의 상세는 링크된 스펙 문서에 있다. 여기서는 **무엇을 만드는지**만 정의한다.

### 7.1 홈 — 여행 대시보드

앱을 처음 켰을 때 보이는 화면. "지금까지 얼마나 여행했는가"를 보여주는 것이 목적이다.

- **다음 여행 카드**: D-day, 목적지 현재 날씨, 첫 일정, 항공편 출발까지 남은 시간
- **여행 통계**: 총 여행 수 / 방문 국가 수 / 방문 도시 수 / 총 여행 일수 / 총 이동 거리 / 방문 장소 수
- **세계 지도**: 방문 국가 채색 (SVG. 지도 API 호출 비용 0)
- **연도별 타임라인**: 올해 여행 몇 번, 며칠
- **최근 여행 카드 리스트** → 탭하면 계획 탭으로 이동
- **빈 상태**: 여행이 0개일 때는 통계 대신 "첫 여행 만들기" CTA + 샘플 여행 둘러보기

→ 상세: [`specs/02-screens.md` §2](specs/02-screens.md)

### 7.2 계획 — 일정 편집기

레퍼런스 이미지의 구조를 따르되, **지도 경로 렌더링은 기존 것을 유지**한다.

- 상단: 여행명 + 기간, 지도/목록 토글, **바우처 보관함 아이콘**, 공유 아이콘
- 액션 칩: `+ 항공편`, `가계부`, `+ 서류 등록`
- **Day 칩** 가로 스크롤 (Day 1 … Day N)
- **일자 헤더**: `5/20 (수) ☀️ 16°/23°` + 편집 버튼
- **타임라인**: 번호 마커 → 항목 카드 (시간 · 카테고리 · 이름 · 메모 · **우측에 날씨 아이콘 + 현재 기온**)
- **구간 라벨**: 항목 사이에 이동 거리/시간 (`73.2km`, `900m`) — `DirectionsService` 결과의 `legs[0].distance/duration` 사용
- **항공편 카드**: 타임라인 최상단에 별도 스타일 (`인천 08:00 → 나리타 11:00 / KE801 / 제2터미널`)
- **지도 뷰**: 번호 핀 + 구간 경로 + 드래그 가능한 바텀시트

→ 상세: [`specs/02-screens.md` §3](specs/02-screens.md)

### 7.3 예약 서류 자동 인식

사용자가 항공권/호텔 예약 PDF를 넣으면 일정이 자동으로 채워진다.

지원 문서: **항공권 e-티켓, 호텔 예약확인서, 렌터카, 철도(신칸센/유레일), 투어·액티비티 바우처, 여행자보험**
지원 형식: PDF, JPG/PNG, Apple Wallet `.pkpass`, `.ics`

핵심 원칙 3가지:
1. **절대 조용히 자동 확정하지 않는다.** 파싱 결과는 항상 검수 시트를 거친다. 신뢰도 낮은 필드는 노란색으로 강조한다.
2. **민감정보는 LLM에 보내기 전에 마스킹한다.** 여권번호·카드번호·생년월일은 정규식으로 제거한다.
3. **원본은 바우처로 보관한다.** Supabase Storage 비공개 버킷 + 오프라인 캐시.

→ 상세: [`specs/04-document-ai.md`](specs/04-document-ai.md)

### 7.4 커뮤니티

여행지별 채널 + 사용자 글.

- 상단: 구독 중인 여행지 채널 가로 리스트
- 탭: `전체` / `구독`
- 글: 텍스트 + 이미지 최대 10장 + 여행지 태그 + (선택) 내 일정 공유 카드
- 댓글(1단계 대댓글), 좋아요, 사용자 팔로우
- **App Store 1.2 필수 장치**: 자동 콘텐츠 필터 · 신고 · 차단 · 24시간 내 처리 · 개발자 연락처 공개

> ⚠️ **이 네 가지가 없으면 App Store에서 리젝된다.** 커뮤니티 기능은 모더레이션과 같은 PR에서 함께 머지한다. 기능만 먼저 내보내는 것을 금지한다.

→ 상세: [`specs/06-community.md`](specs/06-community.md)

### 7.5 설정

계정, 언어(ko/en/zh-CN), 테마(시스템/라이트/다크), 단위(°C/°F, km/mi), 알림, 데이터 내보내기, **계정 삭제**, 약관·개인정보처리방침, 문의하기, 앱 버전.

### 7.6 다국어

한국어 / English / 简体中文. UI 문자열뿐 아니라 **여행지 이름·설명, 푸시 알림, 약관, App Store 스토어 리스팅**까지 포함한다.

주의할 함정 두 가지:
- 현재 `* { word-break: keep-all }`은 한국어용 최적화다. 중국어에서는 줄바꿈이 깨지므로 locale별로 분기해야 한다 (P5).
- **Pretendard 폰트는 간체 중국어 글리프를 충분히 담고 있지 않다.** zh 로케일에서는 `Noto Sans SC`를 함께 로드해야 한다.

→ 상세: [`specs/07-i18n.md`](specs/07-i18n.md)

## 9. 개발 로드맵

**가정**: 풀스택 개발자 2명 + 디자이너 0.5명. 1 스프린트 = 2주.

## 13. 수익화 — 설계만, 3.0에서는 구현하지 않음

### 13.1 결정

**3.0은 과금 코드 없이 출시한다.** 모든 기능이 잠금 없이 열려 있다.

근거: 결제를 붙이면 StoreKit 2 연동, 영수증 검증, 구매 복원, 환불 처리, 가이드라인 3.1.1 대응, 세금·사업자 설정이 따라온다. 최소 2~3주가 추가되고, 그만큼 출시가 늦어진다. **아직 사용자가 없는 상태에서 가격을 정하는 것은 추측이다.** 실제 사용 데이터를 보고 정하는 편이 훨씬 정확하다.

### 13.2 두 가지 후보 모델 (아직 확정하지 않음)

| | **A. 구독** | **B. 프로젝트(여행)별 청구** |
|---|---|---|
| 형태 | 월 ₩4,900 / 연 ₩39,000 | 여행 1건당 ₩3,900~5,900 언락 |
| App Store 상품 유형 | 자동 갱신 구독 | 비소비성 또는 소비성 IAP |
| 매출 예측 | 쉬움 (MRR) | 어려움 (여행 시즌 편중) |
| 사용자 저항 | **높음** — 여행은 연 1~2회인데 매달 청구된다 | **낮음** — 돈 내는 시점과 쓰는 시점이 일치한다 |
| 비수기 이탈 | 큼 | 없음 (애초에 구독이 아님) |
| 원가와의 정합성 | 느슨함 | **좋음** — 비용(지도·LLM 호출)이 여행 단위로 발생한다 |
| 리텐션 압박 | 매달 해지를 고민하게 만듦 | 없음 |

> **현재 기울어진 방향은 B(여행별 청구) 또는 혼합형이다.** 여행 앱의 사용 패턴이 간헐적이고, 실제 원가(Maps·문서 파싱)가 여행 단위로 발생하므로 원가와 과금 단위가 맞는다. 혼합형은 "기본 무료 + 여행당 언락 + 자주 다니는 사람용 구독"이다.
>
> **단, 이 판단은 데이터 없이 내린 것이다.** §13.4의 계측 결과를 보고 확정한다.

### 13.3 3.0에서 **지금 해둬야 하는 것** (이것만 하면 나중이 쉽다)

과금 테이블을 미리 만들 필요는 없다. Postgres에서 컬럼·테이블 추가는 비파괴적이라 나중에 붙여도 된다. 진짜로 지금 해둬야 하는 것은 아래 세 가지다.

**① 기능 게이팅 지점을 한 곳에 모은다**

나중에 "이 기능은 유료"를 넣을 때 코드를 여기저기 고치지 않으려면, 판단 지점이 하나여야 한다.

```ts
// src/shared/entitlements.ts — 3.0에서는 전부 true를 반환한다
export type Feature =
  | 'trip.create'          // 여행 생성
  | 'document.parse'       // 서류 자동 인식
  | 'voucher.storage'      // 바우처 보관 용량
  | 'offline.maps'         // 오프라인 지도
  | 'trip.collaborate';    // 동행자 공유

export function can(feature: Feature, ctx: Ctx): boolean {
  // 3.0: 과금 없음 — 모든 기능 허용
  // 4.0: 여기서만 구독/여행별 결제 상태를 확인하면 된다
  return true;
}
```

**규칙**: 위 기능들을 호출하는 모든 지점은 3.0에서도 `can()`을 거친다. 항상 `true`를 반환하더라도 **호출부를 지금 심어 둔다.** 나중에 함수 본문만 바꾸면 끝난다.

**② 사용량을 지금부터 계측한다**

가격을 정하려면 "사용자당 월 서류 파싱 몇 건, 여행 몇 개"를 알아야 한다. 출시 후에 붙이면 6개월치 데이터를 잃는다.

→ `usage_events` 테이블: [`specs/03-data-model.md` §9](specs/03-data-model.md)

**③ 남용 방어선을 둔다 (과금 게이트가 아니라 비용 방어)**

과금이 없다고 해서 무제한으로 열어 두면 안 된다. 서류 파싱 1건에 LLM 비용이 들고, 지도 호출도 과금된다. **한 명이 스크립트로 수천 건을 돌리면 예산이 하루에 소진된다.**

| 엔드포인트 | 3.0 한도 | 성격 |
|---|---|---|
| 서류 파싱 | 사용자당 **하루 30건** | 일반 사용자는 여행당 5~10건이라 체감 없음 |
| AI 주변 추천 | 사용자당 하루 100건 | 기존 `api/recommend.js` 레이트리밋 승계 |
| 바우처 저장 | 사용자당 **총 500MB** | |
| 여행 생성 | 사용자당 하루 20건 | |

- 이것은 **남용 방어이지 수익화가 아니다.** 한도에 걸린 사용자에게 "유료로 올리세요"가 아니라 "잠시 후 다시 시도해 주세요"를 보여준다.
- 한도 도달 이벤트는 반드시 기록한다 → 정상 사용자가 걸리면 한도가 잘못된 것이므로 올린다.

### 13.4 언제 결정하는가

날짜가 아니라 **신호**로 정한다.

| 신호 | 그때 하는 일 |
|---|---|
| MAU 1,000 달성 또는 월 인프라 비용 $300 초과 | 사용량 데이터로 A/B 모델 중 선택 |
| 사용자당 월 서류 파싱 중앙값 확인 | 여행당 언락 가격 산정 |
| 리텐션 D30 확인 | 구독 적합성 판단 (낮으면 B가 맞다) |

### 13.5 결제를 넣을 때 추가로 필요한 작업 (4.0 견적)

- StoreKit 2 연동 (Capacitor 플러그인 또는 네이티브 브리지) — 1주
- 서버 영수증 검증 (App Store Server API) + 구독 상태 동기화 — 1주
- 구매 복원, 환불·만료 처리, 가족 공유 고려 — 0.5주
- 가격 현지화 (한국/미국/중화권), 세금 설정 — 0.5주
- 가이드라인 3.1.1 대응, 구독 관리 링크, 해지 안내 — 0.5주
- **재심사 필요** (IAP 추가는 새 심사 대상)

**합계 약 3.5주.** 3.0에서 이걸 안 하기로 한 이유가 이 숫자다.

## 15. 용어집

| 용어 | 의미 |
|---|---|
| **Trip** | 여행 1건 (기간·통화·목적지를 가짐) |
| **Day** | 여행의 하루. `day_index`(1부터) + 실제 날짜 |
| **Itinerary Item** | 일정 항목 (장소·식사·숙소·이동·항공 등) |
| **Leg** | 두 항목 사이의 이동 구간. 거리·소요시간·경로를 캐시 |
| **Zone** | 하루 안에서 지리적으로 분리된 항목 묶음 (기존 `computeDayZones`) |
| **Booking** | 파싱된 예약 1건 (항공/숙소/렌터카 등) |
| **Document** | 사용자가 올린 원본 파일. Booking의 근거이자 바우처 |
| **Voucher** | 사용자가 현장에서 제시하는 Document의 열람 형태 |
| **Destination** | 커뮤니티의 여행지 채널 (큐레이션된 목록) |
